## Failures, deterministic repairs and reruns

1. **Initial generation overstatement.** Supplied profile 01 described listed skills as experience (two audit issues); profile 03 implied completed graduation; profile 05 used a backend headline without citing the supporting project/experience. The initial isolation profile 01 also described skills as experience. Generation was tightened to distinguish skills from practice, avoid inferred graduation and cite the facts needed for backend wording. The validator and export gate were unchanged.
2. **Initial incomplete-agent quality.** The first question collected name/contact before clarifying the ambiguous role. The harness answered contact absence without the supplied name, and later answered the repeated name question with a target-role fallback. Its question-count check missed repeated questions. The agent prompt now prioritises ambiguous roles, the reply helper answers supplied names including combined name/contact requests, and repeated questions cause an explicit failure.
3. **Repair 1 evidence.** Six new deterministic cases failed before implementation, then passed. The supplied-five rerun deliberately selected only 01/03/05; all three audits/gates passed. The initial records were not changed. The isolation rerun remained isolated but produced a new profile 01 draft described as a developer and implying independent construction of a group API project; semantic validation blocked it. The incomplete-agent rerun clarified the role and then said “Please provide…” for name/contact, which the question-mark heuristic incorrectly rejected.
4. **Repair 2.** Generation guidance now retains the candidate's stated team contributions and avoids unsupported professional identity. Follow-up detection recognises imperative information requests, while a plain request to confirm a complete draft remains permitted. Three new deterministic cases failed before implementation, then passed. Only isolation and incomplete-agent were rerun: both final isolation CVs passed, and the incomplete agent asked useful, distinct follow-ups with supplied answers.
5. **Static checks.** Strict mypy over the runner found an existing `Any` JSON return in `_load_unseen_profile`; an explicit type cast resolved it without runtime behavior changes. Ruff found newly introduced long lines, which were reflowed. One final prompt reflow occurred after the second isolation process had loaded its prompt; the actual prompt used is retained in that run's supplement. The live behavior tests had passed, but the last 103-character Ruff line was still being corrected as that process started. Final lint/type/test gates passed; this ordering deviation is recorded rather than hidden.

The first repair used six failing cases (34 focused cases green afterward); the second used three (37 focused cases green afterward). Prompt tests assert the instructions passed at the API boundary, not semantic correctness. The separate live reruns provide the behavioral observations. No provider or live-model calls run inside pytest.

## Remaining limits

- These are synthetic development cases with adaptive prompt repairs, not a held-out or statistically reliable quality estimate. Results from different prompt revisions must not be pooled as one frozen benchmark.
- Frozen prediction agreement remains low; the three absent expected jobs were not ranked beyond the returned top three. No retrieval tuning was performed.
- Model semantic audits can be conservative and variable. Valid fact IDs alone do not prove every paraphrase; original blocked results remain part of the evidence.
- Two-job tailoring was limited despite both validations passing.
- `exported` means the runner passed the existing hash/evidence gate and recorded the server state. The service runner does not create PDF bytes; earlier sample PDFs and mocked browser checks are separate evidence.
- Complete/incomplete agent runs test collection behavior with draft facts. The incomplete case is bounded to two replies and does not reach full confirmation or job retrieval. Follow-up recognition is a heuristic and still requires human quality review.
- Isolation uses two sequential sessions in one service instance; it does not cover concurrent requests, deployment, persistence or authentication.
- Only logical call counts are available; no wire-retry count, token usage, latency benchmark or billing total was collected. The original manifests retain their pre-run planned status.
